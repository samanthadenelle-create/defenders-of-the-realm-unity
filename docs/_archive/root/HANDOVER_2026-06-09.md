## 2. THE BIG WIN: Village2 camera bug (the 8-hour rabbit hole)

**Symptom:** "hero stuck on the tree," no controllable hero, ~8hrs of failed patching.
**Root cause (found flow-first, commit `4abde65`):** NOT the hero. `CameraModeController` (WO-338)
auto-resolved **TOWN mode** at scene load, which **disables SmartMobileCamera** and **locks the
view to `_townCentre` (origin = Tree of Life)**, running at `[DefaultExecutionOrder(100)]` so it
stomped SMC + every prior band-aid every frame. The hero was fine and off-screen the whole time.
**Fix:** `CameraModeController.EvaluateContext` now gates TOWN mode strictly on
`BuildModeController.IsActive` (base-build only) — matching the owner-validated "close 3rd-person,
pull up only for base-build" decision. Also removed the harmful per-frame `ForceFollowImmediate`
snap in `SmartMobileCamera.LateUpdate` (was causing a screen shake by fighting the SmoothDamp).
Memory updated: `camera-3d-thirdperson-validated`. **Lesson: when "camera stuck / hero invisible,"
check for a SECOND camera writer before touching the hero.**

### 3b. The NavMesh saga (and how it works now — important for continuity)
- Hero moves via **NavMeshAgent** (`HeroLocomotion`) — "hero shares the enemies' NavMesh."
  So **walkability = the baked NavMesh**, not physics colliders.
- The visual floor (`qFloorWood` tiles) only covers the central ±16 plaza → the rest had no
  navmesh → hero trapped in fragmented islands.
- **Fix:** `CastleHubBuilder.BuildNavMeshFloor` lays **invisible** (renderer-OFF, MeshCollider-ON)
  floor planes — full courtyard (90×90), gate bridge, keep-interior bridge, **upper-battlements
  floor + a ~36° ramp** (L2 access). Baked with **Use Geometry = Physics Colliders** (so
  renderer-off planes are collected — this was THE setting that kept getting missed).
- The keep (`Castle_Medieval`) had its **Mesh Collider disabled in-scene** so it stops carving
  the navmesh → the keep is now an intentional **walk-through landmark** (owner's call).
- Owner mental model that cracked it: *"a box with removable parts — visible, solid, and
  blocks-navigation are three separate components you toggle independently."* (Unity's
  GameObject+Component model, derived from experience.)

## 4. 🔴 OPEN #1 — castle camera / diagonal movement

**Symptom (owner):** in the castle, "had to use two arrow keys at once to go straight."
**Diagnosis (NOT fixed — felt issue, needs playtest):**
- `HeroLocomotion` movement is **world-absolute by design** (WO-368, line ~306): `Vector3 move =
  new Vector3(input.x, 0, input.y)` — Up = world +Z, independent of camera.
- So diagonal movement ⇒ the **castle camera is yawed ~45° off the world axes**. In Village2 the
  camera sat aligned (behind on -Z, looking +Z); in the castle it doesn't.
- **Hypothesis to check:** is `SmartMobileCamera` the *active* camera in MainCastle_Hall, and is
  its yaw/offset world-aligned (offset should be ~(0,3.5,-6), no pan-orbit yaw applied)? The
  wiring adds a camera via `Village2Playable.AddSceneDefaultsToActiveScene` — it may be seated at
  a default yaw, or a second camera is showing. Likely a one-value seat fix once seen in-editor.
- **Do NOT blind-fix** — this is felt; verify with the owner at the controls.
