# Core Architecture Plan — Defenders of the Realm

**Project:** Defenders of the Realm (DeNelle Studios)  
**Tech:** Unity 6 LTS + URP (mobile-first: iOS + Android)  
**Genre:** Tower-defense core loop + dungeon-crawler elements  
**Web3:** Native Solana wallet integration (Seeker, Phantom, and adapters)  
**Monetization:** Cosmetic SKR packs + seasonal pass (explicitly no pay-to-win)  
**Status:** Mid-climb on the delivery ladder (see NORTH_STAR.md). Professional modular foundation already in place.

This document is the canonical high-level architecture reference for the game described above. It codifies the professional structure, module boundaries, folder conventions, and how the key features are realized (or planned to be realized) without duplicating the detailed design specs that live in `docs/`.

---

## 1. Guiding Principles (Non-Negotiable)

1. **Modular by Assembly (DeNelle.*)**  
   All first-party gameplay code lives under `Assets/_Modules/`. Each major domain gets its own folder + `.asmdef`. Cross-assembly references are strictly limited (see §3).

2. **Core Is the Only Shared Dependency**  
   `DeNelle.Core` (and the tiny `DeNelle.AI` behavior-tree sub-assembly) may be referenced by everyone. No other first-party assembly may reference another except through Core.

3. **Service Location for Cross-Cutting Concerns**  
   Use the static `CoreServices` registry (in Core) for HUD, Audio, Jupiter swaps, and Wallet signing. Callers **always** null-check (`CoreServices.Hud?....`). Concrete implementations register themselves in Awake / on connect.

4. **Data-Driven + Builder-Authored Content**  
   Complex authored content (Village, certain dungeons) is generated by deterministic Editor builders (`VillageSceneBuilder`, `DungeonSceneBuilder`, etc.) stored in `Assets/Editor/`.  
   Authoritative runtime data lives in `Assets/StreamingAssets/Data/Canonical/*.json` (and selected ScriptableObjects).  
   The long-term north-star is player-authored bases (ladder rung 5+); the builder pattern is the bridge.

5. **Scene Builder Discipline**  
   `Village.unity` (and similar complex scenes) must **never** be hand-edited. Rebuild via the corresponding `Defenders > ... > Build ... Scene` menu (or batchmode `DeNelle.Editor.*Builder`).

6. **Mobile-Scalable + Offline-First**  
   Rendering and world size are solved by streaming/LOD/culling/lightweight assets (polyperfect _M tier, instancing, Addressables).  
   Economy, progression, and base state support offline accrual with server sync when connected.

7. **Deterministic Combat Path (Future-Proof)**  
   Combat systems (ATB, wave resolution, future async PvP) are designed to be replayable headlessly for server validation.

8. **Monetization Guardrails**  
   Only cosmetics (SKR packs), convenience, and seasonal pass content. No power sold for real money. All purchases flow through the `PackStore` / `Wallet` layer.

## 3. Runtime Service & State Patterns

- **CoreServices** (static registry in Core): `Hud`, `Audio`, `Jupiter`, `WalletSigner`. Register/Unregister pattern with reference-equality guards.
- **GameState + Persistence**: `GameStateService`, `SaveSchema`, `SaveMigrator`, `PersistenceBridge`. Supports offline accrual (mines, pets) and backend-authenticated saves (via wallet signer nonce).
- **Scene Flow**: `SceneRouter` + builder-driven initialization. Bootstrap/persistent managers (GameState, Audio, etc.) use `DontDestroyOnLoad`.
- **Data Loading**: Canonical JSON under `StreamingAssets/Data/Canonical/` (enemies, waves, towers, buildings, pets, cosmetics, packs, wallets, etc.) + selected `ScriptableObject` data (`TowerData` etc.).
- **Visual / Animation Pipeline**: Shared animator controllers (built into `Assets/Generated/Animators/`), `VisualFactory`, `EnemyAnimatorFactory`, skinning via Addressables or Resources. Humanoid retargeting is canonical (see `docs/ANIMATION_PIPELINE.md`).
- **Input**: LeanTouch (mobile gestures) + keyboard/mouse fallback. Camera controllers (over-shoulder for DTT, follow/pan for village).

## 4. Feature Mapping to Architecture

### Tower Defense Core Loop
- **Primary home**: `DeNelle.Village` + `WaveManager` + enemy systems.
- Structures (Heart, Buildings, Towers, Gates, WallSegments) implement `IDamageableStructure`.
- Waves defined in `waves.json` + runtime spawning with spread + stuck-enemy recovery.
- Two combat presentations:
  - Village wave defense (hero + pet + towers + abilities).
  - PatriciaLight "Defend-the-Tower" (manual-aim tower defense slice with reticle, cooldown rings, pet support).
- Build/repair via `BuildMenu` + `WallRepairController` (initially two options: Tower + Repair).
- Future: player freeform placement (north-star CREATE verb) reuses the same primitives the builders currently drive.

### Dungeon Crawler Elements
- **Primary home**: `DeNelle.Dungeons`.
- Two playable 3D dungeons today: Healer's Cottage (west) and Folk's Old Granary (east).
- Entry via violet portal discs + floating signs in the village (trigger or F-key).
- Dungeons contain navigation, encounters, crafting, lore fragments, Bryn the wanderer (companion).
- Additional dungeon stubs exist for future expansion; built by `DungeonSceneBuilder` / `FolksGranaryBuilder`.

### Native Solana Wallet Integration (Seeker, Phantom, etc.)
- **Primary home**: `DeNelle.Wallet` (providers) + `DeNelle.Web3` (Jupiter) + Core interfaces (`IWalletSigner`, `IJupiterService`).
- `WalletService` + `WalletRegistry` + `SolanaWalletProvider` (real adapters + devnet stub).
- `SeekerBootstrap.cs` and dedicated Android install script (`install-apk-to-seeker.ps1`).
- Canon data: `wallets.json`.
- Payments: `PackStore` + `CryptoPaymentManager` (devnet-stubbed today; real tx signing via connected wallet).
- Never commit secrets: `*.keypair.json`, `**/secrets/`, `*.seed`, `id.json`, test ledgers, etc. (enforced in .gitignore).
- Backend auth for saves uses wallet message signing.

### Mobile (iOS + Android)
- Input: LeanTouch (Plugins/CW) — pinch, drag, tap, with desktop fallbacks.
- Builds: PowerShell scripts + `Assets/Editor/*Build.cs` (Android, Desktop). Seeker-specific deploy.
- Rendering: URP with mobile-friendly settings, lightweight assets (polyperfect _M, curated KayKit subsets, instanced VFX).
- Performance audits and port-notes live in `docs/audit/mobile-performance.md` and `docs/port-notes/`.
- Platform plugins and native bridges go under `Assets/Plugins/` (Android `aar`/java, iOS `mm`/framework as needed). Keep examples trimmed.
- Keystore / signing material never committed (already covered in .gitignore + secrets rules).

### Unity 6 LTS + URP
- Confirmed baseline: `UniversalRenderPipelineGlobalSettings.asset`, volume profiles, URP Lit materials, Shader Graph usage for custom effects.
- All third-party packs (when present) are converted via editor fixers (`PolyperfectUrpFix`, `KayKitMaterials`, TripoMaterialFixer, etc.).
- Generated artifacts (animators, terrain layers, baked data) go to `Assets/Generated/` (gitignored).

### Monetization — Cosmetic SKR Packs + Seasonal Pass (No P2W)
- **Primary homes**: `DeNelle.Wallet` (`PackStore`, `PackCatalog`, `packs.json`) + `DeNelle.Cosmetics` (catalog, appliers, BattlePassData / rewards).
- Currencies: Glimmer (earned/soft) + SKR (premium cosmetic currency).
- All offers are cosmetic, convenience, or seasonal progression. Power (stats, towers, heroes) is never sold.
- Store UI is code-built (UXML has proven unreliable in builds); requires dedicated `PanelSettings` for re-enabling scene wiring.
- Referral / promo systems exist as retention companions (in Core + UI modules).

```

├── _Modules/                  # ALL first-party gameplay code (asmdef per module + README.md required)
│   ├── Core/                  # DeNelle.Core (interfaces, state, services, catalog, AI BT)
│   ├── Village/               # Tower defense
│   ├── Dungeons/              # Dungeon crawler
│   ├── Wallet/                # Solana + PackStore
│   ├── Cosmetics/             # Battle pass + cosmetic catalog
│   ├── Web3/                  # Jupiter etc. (thin; interfaces may live in Core)
│   ├── BattleATB/, Audio/, HUD/, Pets/, Onboarding/, Settings/, ... 
│   └── <NewFeature>/          # New module: own folder + asmdef + README.md
├── Editor/                    # DeNelle.Editor asmdef. Scene builders, tools, build scripts. (serialization bottlenecks touched by one agent at a time)
├── Scenes/                    # Playable scenes + test scenes. Complex ones owned by builders.
├── Generated/                 # Build-time output (animators, terrain, etc.). Gitignored.
├── Resources/                 # Runtime-loaded prefabs, textures, data (curated).
├── StreamingAssets/
│   └── Data/Canonical/        # Authoritative JSON data (enemies.json, waves.json, packs.json, cosmetics.json, wallets.json, ...)
├── Plugins/                   # 3rd-party (LeanTouch/CW kept trimmed). Platform-specific (Android/, iOS/) subfolders when native code arrives.
├── Settings/                  # URP assets, quality settings, InputAction assets, etc.
├── AddressableAssetsData/     # Addressables config + groups (used for skins, larger assets).
├── Art/                       # Curated project art (Tree_Of_Life, Towers, Marketplace, etc.).
├── Audio/                     # Project audio (mixers, music). Large or licensed packs handled carefully.
├── Prefabs/, Materials/, Models/, Shaders/  # Curated. Large source packs are gitignored (see .gitignore).
├── UI Toolkit/                # USS, themes, any UXML (note: runtime UI is primarily code-built).
├── polyperfect/, Medieval Village/, Quaternius/, Mirza Beig/, Spells Pack/, ...  # Asset Store packs (mostly gitignored; only used subsets or catalogs committed).
└── (standard Unity: TextMesh Pro, etc.)

docs/                          # All design, architecture, catalogs, audits, port notes. Indexed by docs/README.md.
├── audit/, qa/, roadmap/, port-notes/
└── (polyperfect-asset-catalog.md, kaykit-asset-catalog.md, DESIGN-DECISIONS.md, monetization-v2-spec.md, ...)

Root (selected)
├── CORE_ARCHITECTURE_PLAN.md  # This file
├── ARCHITECTURE_REFERENCE.md  # Earlier detailed reference (historical context)
├── PROJECT_INDEX.md           # Root file navigation
├── PIPELINE_STATE.md          # Living build state (what is BUILT / WIRED / STUB)
```

**Gitignore & Asset Policy Highlights (see full .gitignore):**
- Large packs (polyperfect/, full KayKit/Models/, Mirza Beig/, Spells Pack/, Tripo source) are **gitignored**. Re-import on clone then run the appropriate `Defenders/Art/Fix ... URP Materials` menu item.
- Secrets: `*.keypair.json`, `id.json`, `**/secrets/`, `*.seed`, `.env*`, keystores, etc. — never committed.
- Generated/, Builds/, Library/, Temp/, test ledgers, etc. — ignored.
- Only the exact prefabs/meshes/effects used in game (or their catalog entries) are committed.

**When adding a new module:**
1. Create `Assets/_Modules/NewName/` + `NewName.asmdef` (references only allowed assemblies, usually just Core or Core + a few peers via interfaces).
2. Create `README.md` inside it (one-liner purpose + key files table).
3. Add row to `Assets/_Modules/README.md`.
4. If cross-cutting, define interface in Core and register via `CoreServices`.
5. Update `PROJECT_INDEX.md` / `docs/README.md` as needed.
6. Prefer data (json/SO) and builders over hard-coded scene state.

## 6. Extension & Implementation Notes

- **New tower / enemy / building**: Add to the relevant `*.json` in Canonical/, implement behavior in Village (or Dungeons), wire via the builder or a runtime spawner. Update catalogs if visual.
- **New wallet provider**: Implement behind the Core `IWalletSigner` (and any provider-specific interface). Add to `WalletRegistry`. Never put private keys in code or repo.
- **New cosmetic or pass reward**: Extend `cosmetics.json` + `BattlePassData`/`BattlePassReward`, implement applier in Cosmetics module. Route purchase through PackStore.
- **New dungeon**: Author geometry via a builder (or curated prefabs), register portal in Village builder, add entry in dungeons/ json.
- **Mobile-specific input or UI**: Extend LeanTouch usage or add platform input abstractions in a thin platform module. Keep UI code-built for build reliability.
- **Addressables vs Resources**: Use Addressables for larger/skin-swappable content; Resources for small guaranteed runtime assets. Profile memory (tools exist in Core/Addressables).
- **Editor bottlenecks**: `VillageSceneBuilder.cs` is explicitly a single-touch serialization bottleneck. Coordinate via work orders / owner.
