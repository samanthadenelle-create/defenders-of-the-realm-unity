## 0. Ground truth — how ground is textured TODAY (source-verified 2026-08-16)

Read this before scoping anything; it is why the phases are shaped the way they are.

1. **The hub exterior is a real Unity Terrain, generated by an editor builder.**
   `Assets/Editor/ExteriorTerrainBuilder.cs` (`DeNelle.Editor.ExteriorTerrainBuilder.BuildExterior`,
   batchmode-safe) builds a 1000x1000 origin-centered Terrain on `Main_Castle_Overworld`, writing
   `Assets/Generated/Terrain/ExteriorTerrainData.asset`. It already paints **five splat layers**:
   `Assets/Generated/Terrain/Exterior_Grass.terrainlayer`, `Exterior_Stone`, `Exterior_Mud`,
   `Exterior_Snow`, `Exterior_Dead` — and already heightmaps **four directional biomes**
   (N forest/snow, E farmland, S barren "Wound", W river valley).
2. **CRITICAL GOTCHA — the baked splatmap does NOT survive into the player build (DEF-108).**
   `Assets/_Modules/Village/World/WorldSceneLoader.cs` (~lines 90-140) detects an all-zero alphamap at
   runtime and **repaints the whole splat per quadrant in code**: E "Goldfields"=grass(layer 0),
   W "Stoneback"=stone(1), S "Mirewood"=mud(2), N "Ashwood"=dead(4), distance-weighted with smooth
   seams. **Any grass-variety work that only edits the editor bake will be invisible on device** —
   Phase 1 must either land in this runtime repaint or fix the persistence first (the file's own
   comment defers "full slope/height biome variety" to exactly that fix).
3. **Interior floors are tile/plane based, not terrain.** The castle courtyard is Quaternius
   `Floor_WoodDark` tiles + invisible walkable nav planes (`Assets/Editor/CastleHubBuilder.cs`,
   `BuildNavMeshFloor` / `CreateInvisibleFloor`); the walled-village interior lays KayKit hex road
   tiles "over the grass floor" (`Assets/Editor/VillageSceneBuilder.Content.cs`, `BuildRoads`).
4. **A biome concept ALREADY EXISTS — twice, with two different vocabularies:**
   - `Assets/Resources/Data/Canonical/realm-map.json` (+ byte-identical StreamingAssets copy,
     CanonicalJson law): every region already carries `"biome"` + `"propSet"` — thornwood=forest,
     mirewood=swamp, hollowfrost=ice, emberwastes=fire, starfall-reach=cosmic. Typed surface:
     `Assets/_Modules/Core/World/RealmMapCatalog.cs` (`RealmRegionDef.Biome`, `.PropSet`).
   - `Assets/_Modules/Village/Arena/ArenaBiomeDressing.cs` (WO-499): six biome keys
     (forest/cavern/ruins/volcanic/dungeon/castle) driving arena backdrops + per-biome particles.
   **This WO must NOT mint a third vocabulary** — Phase 2 defines the canonical set and maps both
   existing ones onto it.
5. **Village2** (the raid town) has its own terrain; the injector
   (`Assets/Editor/VillageSceneBuilder.Village2Inject.cs`) raycast-seats buildings onto it
   (`SeatBuildingOnGround`), and `Assets/Editor/Village2Playable.cs` levels the terrain to Y=0.
6. **Asset packs:** KayKit + Quaternius live under `Assets/Models/...` (tracked); polyperfect is
   **gitignored** (CLAUDE.md sec 4 — warn-don't-error on missing prefabs, `_M` tier only). Ground
   textures for new layers should prefer tracked sources or new small textures under
   `Assets/Generated/Terrain/` so a fresh clone still builds.
7. **Town structures/items were researched for the retracted amendment and are now OUT OF SCOPE**
   (owner: "leave all town buildings alone. No VFX."). For the record, so no seat re-researches:
   the single creation path is `Assets/_Modules/Village/Catalog/StructureFactory.cs` (WO-148) over
   `Assets/_Modules/Core/Catalog/CatalogEntry.cs` (`visualPrefabPath` = LOOK) and `RepoProps.cs`
   (BEHAVIOR), skinned by `Assets/_Modules/Village/VisualFactory.cs`, fit-to-height per WO-764
   (`YHeightVariable 4 m * repo.heightMul`; DEF-208/WO-751 normalization). None of these files are
   touched by this WO.

## Phase 1 — Grass/ground texture VARIETY in the hub + Village2 (ship first)

Goal: the ground stops reading as one flat repeat. Data-driven material/layer variants; **zero scene
hand-edits** — everything flows through the builders + the runtime repaint (CLAUDE.md sec 3: scene
changes go through `Defenders > Week 3 > Build Village Scene` / batchmode bakes, filed for CLI).

Work items:
1. **Fix or formally accept DEF-108 first** (decision for CLI at implementation): either make the
   baked splatmap persist into the player build, or promote `WorldSceneLoader`'s runtime repaint to
   the *designed* system. Whichever wins, there must be ONE authority for the splat; today the editor
   bake and the runtime repaint disagree and only the runtime one is ever seen on device.
2. **Add intra-biome variety to the splat**: within each quadrant, blend 2-3 layers by slope +
   height + low-frequency noise (the rules `ExteriorTerrainBuilder` already computes at bake time),
   instead of the current single-layer-per-quadrant fill. Add up to 2-3 new `.terrainlayer` assets
   (e.g. a second grass with different tiling/normal, a dry-turf, a gravel) under
   `Assets/Generated/Terrain/` — Unity terrains support up to 8 layers comfortably on mobile.
3. **Break the tiling**: per-layer tiling-size offsets + a detail/noise blend so the repeat period is
   not visible from the gameplay camera height.
4. **Village2 terrain gets the same treatment** through its own bake path (`Village2Playable.cs` /
   the Village2 injector lane) — reusing the identical layer assets and blend code, not a copy.
5. **Data-driven from day one**: the layer list + blend weights per area live in a data file (see
   Phase 2's `biomes.json` — Phase 1 may start it with just `elarion-hub` and `village2` entries),
   never as new hardcoded constants scattered in two builders.

Files/systems touched: `Assets/Editor/ExteriorTerrainBuilder.cs`,
`Assets/_Modules/Village/World/WorldSceneLoader.cs`, `Assets/Generated/Terrain/*` (new layer assets),
`Assets/Editor/Village2Playable.cs` (or the Village2 bake entry CLI selects), new data file (below).

## Phase 2 — Per-area BIOME DEFINITION (biomes.json)

Goal: one canonical, catalog-shaped mapping `areaId -> { groundLayers, blendRules, propSet,
skySettings }`. (No `ambientFx` field — "No VFX" ruling above; variety is materials/textures/props
only.)

1. **New canonical file `biomes.json`** under `Assets/Resources/Data/Canonical/` + byte-identical
   `Assets/StreamingAssets/Data/Canonical/` copy (CanonicalJson law — mirror how `realm-map.json`
   does it). Typed loader `BiomeCatalog` in `Assets/_Modules/Core/World/` **mirroring
   `RealmMapCatalog.cs` exactly** (static surface + EnsureLoaded via CanonicalJson, Guard.Try-wrapped
   parse, empty-catalog-never-throw). Do not author a second biome list in C# constants.
2. **Reconcile the two existing vocabularies**: the catalog's canonical keys must cover
   realm-map.json's `biome` values (forest/swamp/ice/fire/cosmic) and provide a mapping for
   `ArenaBiomeDressing`'s six arena keys (forest/cavern/ruins/volcanic/dungeon/castle). Existing
   consumers keep working; `ArenaBiomeDressing.ResolveBiome`'s alias table is the model for folding.
3. **Consumers**: the terrain bake/repaint (Phase 1) reads its layer set from the catalog; the prop
   scatter (`ExteriorTerrainBuilder` trees/rocks/ground clutter) reads `propSet`. No particle/VFX
   consumer — per the "No VFX" ruling, biome mood is carried by ground textures, props, and
   sky/fog RenderSettings only.
4. **No save-schema change** — biomes are presentation data derived from area identity; nothing is
   persisted per-player.

## Owner decision points (answer on review — none block Phase 1 item 1-3 prep)

- **D1 — Canonical biome list.** Proposed starting set (superset of both existing vocabularies):
  forest, swamp, ice, fire/volcanic, cosmic, cavern, ruins, castle. Trim or extend?
- **D2 — Differentiation language.** Owner is colorblind: biomes will be distinguished by **texture
  scale/pattern (fine grass vs coarse rock vs cracked mud), ground shape (flat/rolling/jagged),
  value contrast (light snow vs dark dead ground), and prop silhouette** — never by hue names. The
  gate is the greyscale check (AC-1). Decision asked as behavior: should biome identity be readable
  at a glance from the gameplay camera (strong value contrast), or subtle-ambient (variety without
  strong zone edges)?
- **D3 — Hub quadrant identity.** Keep the existing Goldfields/Stoneback/Mirewood/Ashwood quadrant
  scheme as the hub's four "biomes" and only add intra-quadrant variety (recommended, smallest
  change), or re-map hub quadrants onto the Phase 2 canonical biome set?
- **D4 — DEF-108 direction.** Preference between "fix splat persistence into builds" vs "promote the
  runtime repaint to the designed system"? (CLI will bring evidence; owner picks.)
- **D5 — WWCD check** (memory: design tie-breaker): CoC differentiates its single home ground mostly
  by decoration/props, and biome identity lives in event/scenery sets. Default per that lens:
  hub stays one coherent home look with variety (Phase 1), hard biome identity is for the realm-map
  regions (Phase 3). Confirm?
