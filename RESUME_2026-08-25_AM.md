## ⛔ THE P0 — verify it before trusting a single gate result

`tools/assert-unity-editor-pin.ps1` had no explicit `exit 0` on its success path. In PowerShell an
unset `$LASTEXITCODE` is `$null`, and `$null -ne 0` is **TRUE** — so every caller's guard fired on
SUCCESS and `exit $null` exited **0**.

**Net effect: `run-unity-method.ps1` — the runner every gate in the repo goes through — returned
success WITHOUT LAUNCHING UNITY.** Also affected: `build-windows.ps1`, `build-webgl.ps1`,
`run-tests.ps1`, `tools/run-unity-playmode.ps1`.

A fix was in flight at shutdown (explicit `exit 0` + hardening the five callers' guards against an
unset `$LASTEXITCODE`). **Confirm it landed, and confirm the success path empirically** — run a
gate and check that Unity actually started (a real log with real timestamps, not an instant return).

⚠ **Root cause, recorded so it does not repeat:** WO-1178's acceptance criteria listed only
FAILURE-path tests (exit 9 on a bad pin, exit 8 on a missing marker) and never required proving
that a *correct* pin lets the run proceed. A gate needs acceptance on both paths.
